## Project Issues

When I first began working on this project I planned never to publish it, and I was already falling behind on my in-class work for a Java course at university, so most of it was vibe-coded.

Then I realised how completely vibe-coding a project can, understandably, introduct significant issues to the codebase...

So before I committed all of this, I rewrote most of the system by hand, using AI code assists only minimally for more challening aspects of the project such as a tiling system that made it not awful to use. This brings us to our first issue...

**Absolutely MONOLITHIC main file**
- The main `app.js` file is huge, non-modular, has no tests, and is a pain in the butt for someone who might want to make a PR to do so. I didn't have too big of an issue with this at first, but some of you may have noticed I moved all online services to a seperate directory. Unfortunetely, that really only helped me cut down on the large file by a little bit...
- Debugging and tracing errors - when I add a new feature or change the behavior of an old one, and something gets messed up, instead of just narrowing something down to a few lines in a file that controls said feature, it is trying your best not to break something in the middle of 100s of lines of code in a file that should have been 10...
- Duplicated code - some sections were just copied-and-pasted for the computer's 'Testing Environment' versus the actual iPhone environment. Again, this just introduces more bloat and challenges as time goes on. Simplifiying this will probably be the first thing I do...

**Not even basic tests**
- Currently we don't even have basic tests, like a smoke test to see if the app still boots after a change. I'd really like to change this, because it could assist me, other contributors, and even agents in the debugging process and allow us to push updates to users faster...
- In terms of non-code type testing, I have tested on a small range of devices. iOS 16.1.1, 18.3, and the iOS 27 DB3. This is a very simple project, just using basically WebKit, but I'd like to make sure each user has the best expereince possible. I might add a discord server soon so we can discuss it and other projects...

**Spotify tile issues**

Spotify really doesn't want to give up the ghost in terms of API registrations. We'd have two ways around this - a native rewrite so we could hook the local interfaces for Spotify or Apple Music without jailbreak, but this introduces two issues
- Apple probably wouldn't want this on the App Store, for obvious reasons...
- If I told people to sideload it, IMO, it would ruin the main reason behind making this a PWA - to not take up a sideloading slot...
As I said I don't have a foolproof way around this for now, unfortunately. And until we have enough users I will not be transitioning the locking JSON file server to a database, just because the latency is already almost non-existent.

**Usability issues**
- I really don't like how users have to source their own URL schemes to use the app. I want to add a community sourced list, where people can share their schemes directly from the launcher to a list, if they decide to of course...
- Theme and launcher engine seperation - how does a OneUI theme for the launcher sound? Or a modular JS base for iOS app url sourcing, launching, and arrangement? That's my plan for the project at least...
